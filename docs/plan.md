# Indic Lab Report Explainer: Project Plan

Status: being built section by section. Each section below was confirmed by the project owner before being added.

---

## 1. Confirmed decisions

| Decision | Choice |
|---|---|
| Output languages | Plain simple English, plain simple Hindi (Devanagari, test names kept in English), and Hinglish (Roman script). The user picks one of the three |
| Text generation | LLM writes the explanation from a versioned prompt file; code enforces the rules |
| Extraction | Digital PDFs: read text directly. Photos and scans: OpenCV cleanup plus an OCR engine |
| Report types | CBC, lipid profile, thyroid profile (built in that order) |
| LLM setup | Claude API, hosted. Only structured values are sent, never the raw report |
| Verifier | Code checks (exact numbers, units, flags) plus a narrow LLM check for invented claims and advice phrases |

### Notes and risks on these choices
- **Scope:** three report types is the widest option. To protect the 4-week target, each type is a separate milestone: CBC must be fully working end to end before lipid starts, and lipid before thyroid. If time runs out, ship with the types that are finished.
- **Languages:** three output languages triple the review and test work. Build and finish English first, then Devanagari Hindi, then Hinglish. If time runs short, Hinglish is the first to drop. Hinglish has no standard spelling ("hai", "hain", "he" can all appear), which makes meaning checks harder. The README must name exactly which languages work ("English, Hindi, Hinglish"), not "Indian languages". Hindi and Hinglish output need review by a native Hindi speaker. Numbers and test names stay in English and digits in every language, so the code verifier works exactly on all three.
- **Plain language rule:** summaries use short sentences and everyday words, written for a reader with no medical background (target: understandable to a class 8 student). Medical terms appear only with a one-line meaning.
- **Hosted LLM:** sending only structured values (test name, number, unit, flag) keeps personal details out of API calls. This rule goes in the README.
- **Verifier layering:** the code check is required and decides pass or fail on numbers and flags. The LLM check is an extra layer for claims code cannot see. It must return a strict fixed format, and anything unparseable counts as a rejection.

## 2. Data plan

Sources:
1. **Synthetic reports with answer keys.** Generated by script. Every report has a separate answer key file (JSON) holding the correct name, value, unit, range, and flag. Used for development and for testing the verifier.
2. **Consented real reports (11).** Collected from people who agreed to take part. Mostly digital PDFs, from only 1 to 2 labs.
3. **Public sample reports from lab and health websites (optional).** Collected by hand from "sample report" links. Used to widen lab variety, since the consented reports cover few labs.

### Consented reports: rules
Consent scope (confirmed by the project owner): values may be sent to the hosted LLM API during testing; redacted results may be shown publicly. Keep a written or screenshot record of each person's consent, with the date.

- Redact before use: name, age, phone, address, patient ID, barcodes and QR codes, doctor name. Keep lab name and layout. Work on copies; keep originals offline, never in Git or cloud folders.
- Folder `data/real_samples/` is in `.gitignore`.
- Split: 4 development reports, 7 locked test reports. Locked reports are not used for debugging. Run them once at the end of each major stage and record the result.
- If code is changed after seeing locked-set results, that set is no longer a clean test. Note this in the README, or get new reports.
- Write an answer key by hand (JSON) for each report, same format as the synthetic keys.
- Do not copy the locked reports' layouts into synthetic templates.
- Only structured values go to the API, never the raw file. Public examples in the README use redacted images only.

### Rules for public samples
- Check each site's terms before using a file.
- Record the source URL and licence note for every file in a `SOURCES.md`.
- Do not use user-uploaded documents from document-sharing sites. They may be real patients' reports with no licence.
- Never train or tune on them. They are a test.

### Reporting rules
- Report accuracy on synthetic data, on the locked consented set, and on public samples separately.
- Report counts, not just percentages (for example "142 of 150 fields correct"). With 7 locked reports, one error moves a percentage a lot.
- State how many labs the real reports come from. At present: 1 to 2, so real-world results are optimistic and cannot be generalised.
- Include a failure analysis in the README: every error, its cause, and whether it was fixed.
- Wording: "validated on 11 consented reports from N labs", never a broader claim.

Risk: low lab variety is the main weakness of the real data. Add 5 to 8 public sample reports from other labs as a separate test group, and say which results came from which group.

## 3. Output

- Summary shown as text on screen, in English, Hindi, or Hinglish as the user chooses.
- Downloadable PDF of the same summary, with the safety disclaimer and the extracted values table included.
- The PDF is generated only from text that passed both verification gates.
- No audio in the MVP.

---

## 4. Data retention

- Uploaded reports, extracted values, and generated PDFs are kept for 24 hours, then deleted automatically by a scheduled job.
- No user accounts. Access to a result is by a long random link token that cannot be guessed.
- User can delete their report and outputs at any time before the 24 hours end.
- A consent screen is shown before upload, stating what is stored and for how long (DPDP Act).
- Only structured values go to the hosted LLM, never the raw file.

Risks:
- Anyone with the link can see the result, so the link must be random, long, and never logged in plain form.
- The deletion job must be tested: create a report, wait past the limit, confirm the files and database rows are gone.

---

## 5. When the verifier rejects a summary

1. Retry generation once.
2. If it fails again, show only the extracted values table with low / normal / high flags and the safety disclaimer. No generated text is shown.
3. Log the failure reason (without personal data) so failures can be counted and reported in the README.

Rule: unverified text never reaches the user.

## 6. Safety wording and likely causes

Decision (project owner): the summary includes likely causes for each abnormal value, generated by the LLM.

Recorded concern: generated causes cannot be checked against the report, so they sit outside what the code verifier guarantees, and they move closer to diagnosis. The owner chose to keep them, so the following controls apply.

Rules:
- Causes appear only for values flagged low or high by the plain-code flag engine.
- Wording must be general and hedged: "can be associated with", "sometimes seen in". Never "you have", "this means you have", or "this is caused by".
- Never name a specific disease as the explanation for this person. General categories and common non-disease factors (hydration, recent illness, diet, medicines) are allowed.
- Never suggest medicines, supplements, doses, or treatment.
- Every abnormal value ends with: "please discuss this with your doctor".
- The narrow LLM check rejects any cause text that states a certain cause, names a treatment, or uses diagnostic phrasing.
- Safety disclaimer on every screen and every PDF.
- The README states clearly: "Numbers, units, and flags are verified against the report. Cause explanations are general information, are not verified against the report, and are not medical advice."

Tests required before launch:
- A test file of cause sentences that must be rejected (certain-cause wording, treatment advice, named diagnosis).
- A test file of acceptable hedged sentences that must pass.
- A native Hindi speaker reviews a sample of Hindi and Hinglish cause text.

## 7. Success metrics (targets, to be measured)

1. **Extraction accuracy.** Share of fields (test name, value, unit, range) extracted correctly. Reported separately for synthetic reports and for public sample reports, and per report type. Target 95% or more on synthetic; the real-sample figure is reported as measured, with the exact number of samples.
2. **Verifier catch rate.** A test file of deliberately wrong sentences (wrong number, wrong unit, wrong flag, flag stated on a normal value). Target: 100% rejected by the code verifier. Acceptable sentences must not be wrongly rejected, so the pass rate on the correct set is reported too.

Also required, but not headline metrics: the cause-text rejection tests from section 6.

## 10. Extraction approach

Order of attempts for each uploaded file:
1. **Digital PDF with real text:** read the text and table cells directly from the PDF (for example with pdfplumber). No OCR, nearly exact.
2. **Photo or scanned PDF:** clean up with OpenCV (straighten tilt, fix perspective, remove shadows, sharpen, increase contrast), find the table and its cells, then read each cell with an OCR engine.
3. **Always:** show the extracted values to the user to confirm or correct before any explanation is generated.

Notes:
- OpenCV is used for image cleanup and table detection. It is not relied on to read the digits.
- The OCR engine is chosen in week 2 by testing candidates on the synthetic set and on public samples, and the winner is recorded with its accuracy numbers.
- Digits are the main risk (7.2 read as 72, decimal points lost). After extraction, plain-code sanity checks flag impossible values (for example a haemoglobin of 72) for user confirmation.

## 11. Prompts for the LLM

- The app calls the API with system prompts stored as versioned files, for example `prompts/explain_en_v1.md`, `prompts/explain_hi_v1.md`, `prompts/check_v1.md`. These are prompts, not Claude app skills.
- The explanation prompt receives only structured values: test name, value, unit, printed range, flag. It never receives the raw report or personal details.
- The explanation prompt must require: plain simple language, short sentences, hedged cause wording, no diagnosis or treatment, "please discuss this with your doctor" on every abnormal value, and numbers copied exactly.
- The narrow check prompt must return a fixed JSON format. Anything unparseable counts as a rejection.
- A prompt is a request, not a guarantee. The code verifier and the cause rejection tests enforce the rules; the prompt only makes failures less frequent.
- Every prompt change is versioned and re-run against the full test files before use.
